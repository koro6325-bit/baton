## 1. サービス概要

- このサービスはどんなサービスか
  入院中の大切な人を見守るための、チーム専用の超シンプルタイムライン＆医療メモアプリ「ばとん」です。

- 誰の、どんな課題を、どう解決するか
  「連絡ツールに不慣れで連携が難しいメンバーを含む、見守りチーム」の、「LINEだと他の連絡に埋もれて心が疲弊し、何から手をつけていいか分からなくなる」という課題を、情報を入院関係だけに集約し、お薬や持病をワンタップで医師に提示できる専用の場所を提供することで解決します。

---

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情


- いつ：2026年9月、卒業制作の企画を決定しようとしていたまさにそのタイミングで
- どんな状況で：私の祖父母が入院を繰り返すようになりました。容態が心配で電話もできず、心が落ち着かない日々が始まりました。周囲で「誰がいつ荷物を持っていくか」「お医者さんから何と言われたか」を連携しようとしましたが、メンバーの中にはLINEの操作に不慣れな人もおり、スムーズな情報共有ができませんでした。
- どんな気持ちになったか：さらに、自分のLINEには仕事や友人からの連絡も同時に届くため、精神的に「心が忙しく」なり、どの情報から手をつけたらいいのか分からなくなり、強い不安と孤独感に襲われました。



---

### 2-2. なぜそれが「気になった」のか


- 自分の性格・過去の経験・大切にしている価値観：
  私自身が大切な人を想う気持ちが強いからこそ、「大切な人の危機なのに、連絡のストレスや情報の錯綜で自分の心が疲弊していくこと」に強い違和感と悔しさを覚えたためです。また、看病や見守りというデリケートな状況だからこそ、日常のノイズ（仕事や趣味の連絡）から完全に切り離された、「その人のことだけに心を集中できる穏やかな場所」が絶対に必要だと痛感したからです。

## 3. 課題の整理（表面的になっていないか）

### 3-1. 表に見えている困りごと

- LINEのグループトークだと、お見舞いの予定や医師からの伝言がすぐに流れてしまい、見返せない。
- メンバーの中にLINEをやっていない、または操作に不慣れな人がいて、連携の輪から外れてしまう。
- 病院の受付や診察室で、医師から「普段の持病や薬は？」と聞かれた際、詳細を知る特定のメンバーに確認をとるか、LINEの過去ログを必死に遡って探さなければならず、すぐに説明できない。

---

### 3-2. 本当に解決したい課題は何か


- なぜ？ ➔ 日常の連絡と混ざり合い、情報が埋もれて見失うから。
- なぜ？ ➔ 「誰が何をしたか」が分からず、特定のメンバーに見守りの負担や確認の連絡が集中し、チーム全員の心の余裕がなくなるから。
- なぜ？ ➔ 不安と焦りで心が忙しくなり、一番大切であるはずの「入院している本人の心に寄り添うこと」に集中できなくなるから。

→ 本当に解決したい課題：非常時（入院・看病）において、関係者間の情報錯綜やコミュニケーション不全によって引き起こされる「精神的な疲弊と、それによる見守りへの集中力の低下」。

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー


年齢設定：
  - 年齢：50代〜60代の子供世代、および20代〜30代の孫世代・パートナー層
  - 理由：なぜ他の年代ではなく、この年代にあなたのアプリが必要、または使ってもらいやすいのでしょうか？
    ➔ 大切な人の突然の入院に直面し、仕事や日常生活を送りながら交代で見守りやお見舞いを行う必要がある世代だからです。

生活・状況設定：
  - 生活・状況：離れて暮らす大切な人が急に入院し、親族や関係者でシフトを組んで洗濯物の回収や荷物届け、医師からの病状説明の聞き取りを行っている状況。
  - 理由：その場面で発生する課題を、アプリを使うことでどう解決できますか？
    ➔ 日々変化する状況を正確にシェアし合わないと、荷物の届け重複や、連絡の抜け漏れが発生するのを防ぐためです。

環境設定：
  - 環境：スマホの複雑な操作（LINEのアルバム機能やカレンダーアプリの共有設定など）が苦手なシニア層や、血縁関係に縛られず多様な形態で集まった見守りチーム。
  - 理由：その環境特有のハードルを、アプリの仕組みでどう解消しますか？
    ➔ 「文字を入力してボタンを押すだけ」という極限までシンプルなUIにすることで操作のハードルを解消し、同時に「家族」という言葉を使わないことで、様々な関係性のチームが心理的抵抗なく使えるようにします。

### 5-2. それでも自分が作りたい理由

LINEは非常に便利ですが、スタンプや日常の雑談、仕事の通知などが同じ画面に混在するため、非常時の見守りにおいては「通知を見るだけで心が休まらなくなる（心が忙しくなる）」という弊害があります。また、過去に投稿した「お薬手帳の写真」や「先生からの伝言」がトーク履歴の彼方に流れてしまい、病院の受付という一番焦っている場面でパッと見つけられないというズレがありました。

### 5-3. 差別化を「体験価値」で表現する

- 私のアプリの差別化ポイント：
  複雑な操作に不慣れな人でも迷わない「ボタンを押すだけのカテゴリ別投稿」と、診察室で焦らずワンタップで医師に提示できる「お守り医療メモ」により、【急な入院で心が落ち着かない見守りチーム】が、【病院の診察室やお見舞いの現場】で、ノイズに惑わされず見守りだけに心を集中できる体験を提供します。

## 7. このアプリで実現すること

### MVPで作る機能
1. ユーザー登録・ログイン機能（見守り部屋の作成・URL招待による参加機能）
2. 超シンプルなカテゴリ別タイムライン機能（CRUD）
   - 「本人の様子」「お見舞い・荷物」「手続き・その他」の3つのボタンからテキスト投稿。
   - 投稿された内容は、カテゴリ別のタブで切り替えて閲覧可能（情報が流れない）。
3. お守り医療メモ機能（対象者プロフィール）
   - 1人分の「持病」「かかりつけ医」のテキスト登録、およびお薬手帳の写真アップロード（Active Storage活用）。
   - ※編集権限について（意図的な割り切り理由）：MVPでは、現場における「メンバー全員がその場で素早く情報を更新・共有できるスピード」を最優先とするため、あえて編集権限を絞らず、グループ内の全員が一律で編集できるシンプルな設計にしています（本リリース以降で主担当者のみの制限などを検討）。
4. 【愛着・温かみ要素】見守りチームの愛称表示＆お疲れ様メッセージ表示
   - 殺伐としがちな看病現場の空気をふっと和ませるため、ヘッダーに「〇〇（設定したチーム名・愛称）のばとん日記」と表示。また、投稿完了時に「いつもお疲れ様です、一息ついてくださいね」といったランダムな労い文言を表示する仕組みを、最小限の実装コストで組み込みます。

### 本リリースで作る機能
1. LINE通知連携機能（LINE Notify / LINE Bot）
2. ワンタップ安心ボタン機能（リアクション機能：シニア層でも押しやすいありがとう・お疲れさまスタンプ）
3. カレンダーによるお見舞い・お世話シフト調整機能

## 8. このアプリの懸念点とその対策

### 懸念点①

- 何が問題になりそうか：新しいツールの操作自体を面倒に感じて使わなくなってしまう可能性。
- なぜそう思うか：日常的に使い慣れているLINE以外のアプリを新しく開くこと自体が、シニア層にはハードルになり得るため。
- そのために考えている対策：MVPの段階では、ボタンを大きくし、説明テキストを極限まで減らした「迷いようがないUI」を徹底します。さらに、本リリース以降で「重要な更新だけ使い慣れたLINEに自動通知される仕組み（LINE Notify等）」を取り入れ、スマホを頻繁に開かないメンバーでも異変に気づけるように対策します。

### 懸念点②（セキュリティ面）

- 何が問題になりそうか：招待URL（トークン方式）を知っていれば誰でも部屋に入れてしまうため、セキュリティが緩いと指摘される可能性。
- なぜそう思うか：パスワード認証や厳格な二要素認証を挟んでいないため。
- そのために考えている対策：本アプリはメンバー間の信頼関係を前提としたクローズドな利用シーンを想定しており、招待URLは身内でのみ共有されることを前提としています。ツールに不慣れな層の参加ハードルを極限まで下げることを最優先とした「トレードオフを理解した上での意図的な設計判断」です。なお、技術的なリスク軽減策として、URLに含まれるトークンには SecureRandom.urlsafe_base64(32) を採用し、総当たり（ブルートフォース）による推測を事実上不可能にします。本リリース以降では、万が一のURL流出に対処するための「招待URLの再発行機能」や、管理者の承認制、有効期限設定などの機能追加を検討します。また、通信経路の安全性を担保するため、本番環境でのHTTPS化を徹底します。

## 10. 技術スタック（手段としての技術）

### 10-1. 使用予定の技術

- フレームワーク：Ruby on Rails (v7.x)
- DB：PostgreSQL
- デプロイ先：Render
- 使用予定ライブラリ：Active Storage（画像アップロード用）

---

### 10-2. 技術選定 accomplishments

| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| Ruby on Rails | 採用 | カリキュラムで深く学んでおり、最も素早く安全にCRUD機能と画像アップロード（Active Storage）を実装できるため。看病の時間を確保しつつ、MVPを最短でリリースするのに最適。 |
| React / Next.js | 不採用 | フロントエンドのキャッチアップコストが高く、MVPのリリース速度が落ちるため、まずはRailsのView機能で完結させる。本リリース以降に必要に応じて導入を検討。 |

- 今回チャレンジしたい点：非常時でも誰もが迷わず操作できる、アクセシビリティを追求したUI/UX設計と、情報のノイズを極限まで減らす画面レイアウト。
- 不安な点：実生活の看病とのスケジュール両立。そのため、進捗管理（Issueの見積もり）を通常より細かく行い、いつでも機能を削れるように開発します。
